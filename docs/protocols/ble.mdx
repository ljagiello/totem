The Totem is a **BLE peripheral**; the phone app is the central. The stack is
NimBLE (via MicroPython's `bluetooth`), driven by `f_ble/peripheral.py`,
`ble_controller.py`, `ble_core.py`, and `ble_manager.py`.

## GATT identifiers

Custom 128-bit UUIDs recovered verbatim from the image:

| UUID | Role (inferred) |
| --- | --- |
| `258EAFA5-E914-47DA-95CA-C5AB0DC85B11` | primary Totem service |
| `7913b588-0000-4635-b066-baa2cfc197cf` | transfer service base |
| `7913b588-0001-4635-b066-baa2cfc197cf` | characteristic (e.g. RX / write) |
| `7913b588-0002-4635-b066-baa2cfc197cf` | characteristic (e.g. TX / notify) |

The `7913b588-000x` family uses an incrementing 4th field for the service (`0000`) and
its characteristics (`0001`, `0002`) — the standard write/notify pair for a chunked
serial-style transport. Transfer is implemented in `svc_ble_transfer.py`.

## Advertising

| Symbol | Role |
| --- | --- |
| `ble_advertise`, `gap_advertise` | start advertising |
| `advertise_burst` | short advertising bursts (power saving) |
| `gen_advertise_payload` | build the adv payload |
| `get_device_name`, `device_name_sz` | device name in the payload |
| `manufacturer_id` | manufacturer-specific adv data |

BLE is normally **off to save power** and comes up on demand. The controller logic
(`BleCtrl`) manages this:

```text
[BleCtrl] Starting BLE
[BleCtrl] Stopping BLE for blocker
[BLE Check] Starting advertising burst
[BLE Check] App connected via fast reconnect
[BLE Check] No connection - quietly turning BLE back off
[BleCtrl] Silently reconnecting BLE after blocker cleared
```

A **blocker** system (`BleBlockers`, `Setting BLE block to: {} | for index: {}`) lets
subsystems veto BLE while they need the radio, then BLE silently reconnects when the
last blocker clears.

## Connection handshake

Once connected, the two sides negotiate before app data flows:

<Steps>
  <Step title="MTU exchange">
    `Current MTU: {}` — determines chunk size for the transfer layer.
  </Step>
  <Step title="Connection mode / frame schema">
    `=== BLE Connection Mode: {} | FrameSchemaId: {}` — selects the framing schema
    used for the rest of the session.
  </Step>
  <Step title="ConnStatus Ready">
    The central signals readiness. Until then the device holds off:
    `ConnStatus Ready command not yet received, not sending BLE updates`.
  </Step>
  <Step title="Data transfer">
    Messages flow as `(cat_id, cmd_id)` records (Static, Live, Peer). See
    [message format](/protocols/message-format).
  </Step>
</Steps>

## Half-duplex & comms handoff

The link is **half-duplex** with an explicit transmit owner:

| Symbol / log | Meaning |
| --- | --- |
| `is_tx_owner`, `is_tx_ready` | which side may transmit, and whether it is ready |
| `Half-duplex is used; exiting send_data loop` | yield the link to the peer |
| `BLE ACK Comms Handoff` | acknowledge handoff of the app connection |
| `ble_handoff_watchdog`, `[BLE Watchdog] Handoff stall detected` | recover a stalled owner |

Because Totems mesh, a single phone connection can be **handed off** between bonded
Totems so the app effectively talks to the whole group through whichever Totem currently
owns the link. The watchdog guarantees liveness if an owner stalls.

## Keys & bonding

BLE bonding keys are persisted in `ble_keys.bin`. Pairing/bond management is handled by
the controller (`add_new_bond`, `create_promo_bond`); see also the mesh
[peer bonding](/protocols/espnow-mesh) which is a separate, Totem-to-Totem concept.

## OTA over BLE

`ota_ble.py` + `svc_ble_transfer.py` carry a firmware image over the same chunked GATT
transport for app-driven Bluetooth updates (`Connected to OTA BLE`, `cb_start_ota`,
`close_ota`). This is the "update via the app" path; the WiFi hotspot path is the
fallback. See [OTA](/subsystems/ota).

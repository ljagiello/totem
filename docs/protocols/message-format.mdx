## Addressing: `(cat_id, cmd_id)`

Every application message carries a one-byte **category** and a one-byte **command**.
This tuple is used identically on the BLE link and for peer sync over the mesh.

```text
┌────────┬────────┬───────────────────────────┐
│ cat_id │ cmd_id │ payload (struct-packed)   │
│ 1 byte │ 1 byte │ variable                  │
└────────┴────────┴───────────────────────────┘
```

Evidence: `[BLE] DataXfer cat_id: {} | cmd_id: {}`,
`[BLE] ConnStatus cat_id: {} | cmd_id: {} | len: {}`,
`A cmd_id must be provided for demi-god messages`.

## Categories

Confirmed `(cat_id, cmd_id)` pairs and their labels, taken directly from the
`send_data_v2` transmit logs:

| cat_id | Category | Confirmed commands | Meaning |
| --- | --- | --- | --- |
| `0x01` | **Static Data** | `(0x01, 0x02)` | device config / identity that changes rarely |
| `0x03` | **Live Data** | `(0x03, 0x01)` | real-time state (position, heading, battery) |
| `0x06` | **Peer** | `(0x06, 0x02)` per-peer, `(0x06, 0x07)` Peer Sync | peer list / bond sync between Totems |
| — | **Conn Status** | (handshake) | connection readiness + mode negotiation |

The transmit path names the same set through **command namespaces** (each a `*_cmd_id`
symbol), which correspond to categories/sub-protocols:

| Namespace symbol | Sub-protocol |
| --- | --- |
| `static_data_cmd_id` | Static Data (0x01) |
| `peer_cmd_id` | Peer / mesh sync (0x06) |
| `option_cmd_id` | device options / preferences |
| `wifi_cmd_id` | WiFi credential + hotspot control |
| `ota_cmd` | OTA control (start/close/status) |

ACKs are logged per category and prove the receive side of each:
`BLE ACK Static Data`, `BLE ACK Live Data`, `BLE ACK Peer Ping`, `BLE ACK Peer Sync`,
`BLE ACK Comms Handoff`.

### Full registry: `TOTEM_MSG_MAP` (recovered)

`TOTEM_MSG_MAP` (qstr 590) is a `(cat_id, cmd_id)`-keyed **serialization / handler
registry**, built as a flat map in `espnow_conn_v2.py` and keyed by a 2-byte
`(cat_id, cmd_id)` `bytes` key (byte 0 = `cat_id`, byte 1 = `cmd_id`). Each **value** is
either a payload `struct` format string or a handler / type name — it is *not* a numeric
label map. The 13 entries were recovered in full from the frozen bytecode (**Confirmed**):

| `(cat_id, cmd_id)` | Value | Kind |
| --- | --- | --- |
| `(0x00, 0x00)` | `disconn_animation` | handler / type |
| `(0x00, 0x01)` | `disconn_animation` | handler / type |
| `(0x00, 0x02)` | `disconn_animation` | handler / type |
| `(0x01, 0x00)` | `<BBB7bHbb` | payload struct (14 B) |
| `(0x01, 0x02)` | `<BBiffHii` | payload struct (24 B) |
| `(0x01, 0x05)` | `dev_total_lightsleep_ms` | handler / type |
| `(0x01, 0x06)` | `<BBbbB` | payload struct (6 B) |
| `(0x01, 0x07)` | `<3Bbb` | payload struct (5 B) |
| `(0x02, 0x00)` | `dev_info` | handler / type |
| `(0x03, 0x01)` | `device_power` | handler / type |
| `(0x03, 0x02)` | `device_power` | handler / type |
| `(0x07, 0x00)` | `disabled` | handler / type |
| `(0x07, 0x01)` | `<BBHbffb` | payload struct (15 B) |

Beyond the three cleartext categories, the registry reveals category `0x00`
(`disconn_animation`), `0x02` (`dev_info`), and `0x07` (power / `disabled`). A companion
`EXTENDED` map adds schema-id variants — `(0x00, 0x00)` schemas 25 / 59 / 72,
`(0x01, 0x06)` schemas 5 / 29, and `(0x02, 0x00)` schema 45 (schema 59 →
`<BBffbbhbbb6Bhii4BhHehhffbB`, schema 72 → the same plus a `BiiBBb` tail).

<Info>
`TOTEM_MSG_MAP` is the `(cat_id, cmd_id)`-keyed **serialization / handler registry** — its
values are payload `struct` format strings or handler / type names, not numeric labels. It
does **not** contain category `0x06`: the **Peer** and **Peer Sync** frames
`(0x06, 0x02)` / `(0x06, 0x07)` are handled by separate peer-sync logic, outside this map.
The `Static Data` / `Live Data` names in the table above are cleartext log strings from
`send_data_v2`, not values in this map.
</Info>

## Message identity & lifetime

Mesh/peer messages are de-duplicated and expired:

| Symbol | Role |
| --- | --- |
| `gen_msg_uid` | generate a unique id per message |
| `MSG_EXP_MSECS` | message expiry window |
| `MSG_IN_BUFF`, `MSG_OUT_BUFF` | inbound / outbound message buffers |
| `msg_interval_ms`, `msg_offset_ms` | send scheduling |
| `MESH_PEER_MSG_LIMIT` | per-peer message cap |
| `last_msg_rx`, `last_msg_tx`, `last_msg_ticks` | liveness tracking |

This lets a message flood the mesh once and be dropped as a duplicate on re-receipt
(`Demi-god command ignored, already received` is the same idea in the command path).

## Chunking

Payloads larger than the link MTU are fragmented by a common chunking layer
(`f_ble/chunking.py`). The relevant constants:

| Symbol | Role |
| --- | --- |
| `CHUNK_HDR_FMT` | `struct` format of the per-chunk header |
| `CHUNK_HDR_SZ` | header size in bytes |
| `CHUNK_BUFF_SZ` | chunk buffer size |
| `FrameSchemaId` | negotiated frame schema per connection |

The chunk header prefixes each fragment. Its format and field order are now recovered from
the live `struct.pack_into` call in `chunking.gen_transfer_buff`:
`CHUNK_HDR_FMT` = `<HBBBiHiB` (**`CHUNK_HDR_SZ` = 16 bytes**), written at **offset 2** of
the transfer buffer (`buff[0]` / `buff[1]` are a separate 2-byte frame prefix).

| # | code | Field | Type |
| --- | --- | --- | --- |
| 1 | `H` | `file_id` | uint16 LE |
| 2 | `B` | `status_id` | uint8 |
| 3 | `B` | `action_id` | uint8 |
| 4 | `B` | `file_type_id` | uint8 |
| 5 | `i` | `byte_pos` | int32 LE |
| 6 | `H` | `chunk_no` | uint16 LE |
| 7 | `i` | `file_size` | int32 LE |
| 8 | `B` | reserved (packed as `0`) | uint8 |

The format string and field order are **Confirmed** (decoded from the pack opcode stream);
the `CHUNK_HDR_FMT` name→value binding is **Inferred (high confidence)** — `<HBBBiHiB` is
`chunking`'s only `struct` format and the value imported elsewhere as `CHUNK_HDR_FMT`, but
no literal `CHUNK_HDR_FMT = "…"` assignment was seen in the frozen bytecode.

The header carries **`file_size`** (the total file size), **not** a per-chunk size. Chunk
size appears only in the per-chunk log line below (`Chunk Size: {}`), never in
`CHUNK_HDR_FMT`.

## File transfer

`f_ble/file_upload.py` implements resumable, acknowledged file transfer over the chunk
layer. The per-chunk log line enumerates the protocol fields:

```text
Chunk No: {}/{} | Pct: {:.3f} | File ID: {} | Chunk Size: {} |
Byte Pos: {} | File Size: {} | Run Time: {} | Latency: {} | len: {} | queued: {}
```

Control flow (from `[Upload]` logs):

| Event | Meaning |
| --- | --- |
| `App header | status: {} | action: {} | chunk: {} | err: {}` | transfer control frame |
| `Resuming at chunk {}` | resume an interrupted transfer |
| `Chunk {} acknowledged successfully` | per-chunk ACK |
| `Ignoring header for file_id {} (in flight: {})` | de-dupe concurrent transfers |
| `Streamed {} B in {} chunks | {} ms` | completion summary |
| result codes | `1=done 2=no app 3=retry 4=failed 5=cancel 6=abort` |

Named files moved over this path include `content.json`, `config.json`, `commslog.bin`,
`ble_keys.bin`, `debug.bin`, and AssistNow GNSS data (`assist-now-b.bin`).

## Struct catalog (wire layouts)

Payloads are packed with Python `struct`. The firmware's format strings are recovered
verbatim; each defines a byte-exact record. A representative selection:

| Format | Fields (struct codes) | Likely use |
| --- | --- | --- |
| `<BBB` | cat_id, cmd_id, +1 byte | short header-prefixed record |
| `<BBHbBBiHiB` | mixed bytes/half/int | a live-data / status record |
| `<ffbb...` (e.g. `<ffbb`, `<ffbBih`) | two floats + flags | lat/lon (float32) + flags |
| `<BBffbbbHbbH` | 2 bytes + 2 floats + flags | position + metadata record |
| `<biHBBBbBBBbhhiiibbb` | wide mixed record | full peer/nav telemetry |

<Note>
Dozens of distinct formats are present (see the reference data in the repo). Floats
(`f`) **often** appear in pairs, matching latitude/longitude, but the pairing is not
universal — some records carry a lone or triple float (e.g.
`<bfi3fb4Bi3b2hbiffb3ibHBBb`: a single `f`, then a `3f` group). The leading `BB` matches
the `(cat_id, cmd_id)` header.
</Note>

Several exact format ↔ `(cat_id, cmd_id)` bindings are now recovered from `TOTEM_MSG_MAP`
and its `EXTENDED` companion (**Confirmed**):

| `(cat_id, cmd_id)` | Format | Size |
| --- | --- | --- |
| `(0x01, 0x00)` | `<BBB7bHbb` | 14 B |
| `(0x01, 0x02)` | `<BBiffHii` | 24 B |
| `(0x01, 0x06)` | `<BBbbB` | 6 B |
| `(0x01, 0x07)` | `<3Bbb` | 5 B |
| `(0x07, 0x01)` | `<BBHbffb` | 15 B |
| `(0x00, 0x00)` schema 59 | `<BBffbbhbbb6Bhii4BhHehhffbB` | 57 B |
| `(0x00, 0x00)` schema 72 | `<BBffbbhbbb6Bhii4BhHehhffbBBiiBBb` | 69 B |

Binding the **remaining** formats to a specific message still requires further bytecode
disassembly, but the byte layouts themselves are fully recovered.

The Totem Compass uses the ESP32's single 2.4 GHz radio in three roles. They are
time-multiplexed by the WiFi/BT coexistence layer, never simultaneously active in a way
that conflicts on-air.

## One message model across radios

The most important protocol finding: BLE and the mesh share a **single application
message model**. Every message is addressed by a two-byte tuple:

```text
(cat_id, cmd_id)   +   payload
 │        │
 │        └── command within the category
 └── category (Static Data, Live Data, Peer, …)
```

The BLE link logs it directly — `[BLE] DataXfer cat_id: {} | cmd_id: {}` and
`Conn Status Update | cat_id: {} | cmd_id: {}` — and the same categories drive peer
sync over ESP-NOW. Large BLE file/OTA transfers are fragmented by a shared **chunking**
layer; mesh frames are single fixed-size packets (57 B / 69 B, well under the 250-byte
ESP-NOW MTU). The full model is on the [message format](/protocols/message-format) page.

### Recovered from bytecode

Frozen-MicroPython disassembly (v1.25.0 / .mpy v6.3) has since decoded the three
formerly-pending items. `TOTEM_MSG_MAP` is a **flat** dict built in `espnow_conn_v2.py`,
keyed by the 2-byte `(cat_id, cmd_id)`; each value is either a payload `struct` format or
a handler/type name. Every format string below is a literal in rodata, and the map plus
its bindings are **confirmed** from decoded opcodes.

| `(cat_id, cmd_id)` | Value | Kind |
| --- | --- | --- |
| `(0x00, 0x00)` / `(0x00, 0x01)` / `(0x00, 0x02)` | `disconn_animation` | handler |
| `(0x01, 0x00)` | `<BBB7bHbb` | struct fmt |
| `(0x01, 0x02)` | `<BBiffHii` | struct fmt (Static-Data class) |
| `(0x01, 0x05)` | `dev_total_lightsleep_ms` | handler |
| `(0x01, 0x06)` | `<BBbbB` | struct fmt |
| `(0x01, 0x07)` | `<3Bbb` | struct fmt |
| `(0x02, 0x00)` | `dev_info` | handler |
| `(0x03, 0x01)` / `(0x03, 0x02)` | `device_power` | handler |
| `(0x07, 0x00)` | `disabled` | handler |
| `(0x07, 0x01)` | `<BBHbffb` | struct fmt |

A parallel `EXTENDED` map holds multi-schema variants: `(0x00, 0x00)` schema 59 →
`<BBffbbhbbb6Bhii4BhHehhffbB` (57 B), schema 72 → the same plus a `BiiBBb` tail (69 B) —
these are the fixed-size mesh frames; `(0x01, 0x06)` schema 5 → `<BBbbB`; `(0x02, 0x00)`
schema 45 → `dev_sampling`. Category `0x06` (Peer Sync) is **absent** from this registry —
it is handled by separate peer-sync logic, not the payload-format map.

**`CHUNK_HDR_FMT` = `<HBBBiHiB`** (`CHUNK_HDR_SZ` = 16 B), packed at offset 2 of the
transfer buffer by `chunking.gen_transfer_buff`. Field order: `file_id` (H), `status_id`
(B), `action_id` (B), `file_type_id` (B), `byte_pos` (i), `chunk_no` (H), `file_size` (i),
reserved (B). The packed wire format and field order are **confirmed** from the live
`struct.pack_into`; the `CHUNK_HDR_FMT` name→value binding is **inferred (high
confidence)** — no literal module-level assignment was found in the frozen bytecode.

<Note>
**Verdict.** The protocol's transport, addressing scheme, category taxonomy, GATT
identifiers, connection state machine, chunking/file-transfer, mesh encryption, and the
demi-god command set are **fully captured**. The three items that were previously pending
in bytecode — the per-category `cmd_id` map (`TOTEM_MSG_MAP`), the `struct`-to-message
bindings, and the `CHUNK_HDR_FMT` field order — have now been recovered by disassembling
the frozen MicroPython modules: `TOTEM_MSG_MAP` and its bindings live in
`espnow_conn_v2.py`, and `CHUNK_HDR_FMT` is packed in `f_ble/chunking.py` (see the table
above). See [methodology](/reference/methodology).
</Note>

## Coexistence

ESP-IDF's WiFi/BT coexistence arbitrates the radio. The mesh runs on a fixed home
channel; a peer whose channel differs is rejected (`Peer channel is not equal to the
home channel, send fail!`). During a hotspot OTA the device is a WiFi station on the
phone's channel, and BLE/mesh traffic is suspended for the duration of the download.
